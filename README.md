# SFMC Toolkit for Agents

## About this project

This repo is a toolkit designed to help agents plan and execute migrations into and out of Salesforce Marketing Cloud Engagement (SFMC).

It ships three things that work together:

1. A machine-readable OpenAPI 3.0.3 contract for the SFMC REST surface, annotated with migration-oriented vendor extensions.
2. A library of migration recipes (`specs/migrations/*.yaml`) that describe, step by step, how to import data, assets, and configuration into SFMC or export them out.
3. A small agent-facing surface: an `AGENTS.md` entrypoint, a generated `migration-catalog.json`, and a read-only MCP server stub that exposes lookup tools over stdio.

It is not an official Salesforce export. The OpenAPI spec is community-maintained and normalized from Salesforce's published permission/scope matrix and REST reference pages.

## Who this is for

Primary audience: **agents** (and the humans steering them) performing SFMC import/export migrations.

Secondary audience: human developers building SFMC integrations who want a route map and scope reference. Most of what agents need is useful to humans too.

## What you get

- **OpenAPI contract** at `specs/sfmc_marketing_cloud_openapi.yaml`, with tag-family fragments under `specs/paths/*.yaml`.
- **Migration vendor extensions** on operations: `x-migration-direction`, `x-bulk-capable`, `x-polling-endpoint-of`.
- **SFMC vendor extensions** preserved on every operation: `x-sfmc-permission-ids`, `x-sfmc-user-permission-paths`, `x-sfmc-installed-package-scopes`, `x-original-marketing-cloud-paths`.
- **Recipe library** at `specs/migrations/*.yaml` — one recipe per migration flow (see `AGENTS.md`).
- **Generated catalog** at `dist/migration-catalog.json` — a flattened, agent-friendly index of operations and recipes built from the spec.
- **Postman collection for the SOAP API**, generated by CI as a downloadable artifact and covering Automation Studio: automations, run status, query/import activities, folders, and paging. See [SOAP API: Postman collection](#soap-api-postman-collection).
- **MCP server stub** at `scripts/mcp-server.mjs` — read-only tools (`list_migration_recipes`, `get_migration_recipe`, `get_endpoint_for_task`, `lookup_scope_for_operation`, `describe_operation`, `resolve_polling_target`, `plan_migration`) served over stdio.

## Supported migration directions

- **`import`** — loading contacts, data extension rows, content assets, journey definitions, and related configuration **into SFMC** from an external system.
- **`export`** — extracting the same families **out of SFMC** to another system, file store, or warehouse.

Non-goal: cross-tenant SFMC-to-SFMC orchestration as a single recipe. Compose an `export-*` recipe with an `import-*` recipe instead.

## Quickstart for agents

Start at `AGENTS.md`. It describes how to load the OpenAPI, read the catalog, pick a recipe, and execute steps while honoring scopes, polling relationships, and retry guidance.

To query the repo interactively, run the MCP server:

```bash
npm install
npm run catalog
npm run mcp
```

The server speaks stdio. Example tool calls: `list_migration_recipes`, `get_migration_recipe`, `get_endpoint_for_task`.

## Quickstart for humans

```bash
npm install
npm run catalog     # build dist/migration-catalog.json
npm run build       # build Swagger UI site into dist/
npm run validate    # lint, validate, and run integrity checks
```

Build output:
- `dist/index.html` — interactive Swagger UI
- `dist/sfmc_marketing_cloud_openapi.yaml` + `dist/paths/*.yaml` — copied spec
- `dist/sfmc.yaml` — bundled single-file OpenAPI artifact
- `dist/migrations/*.yaml` — copied recipes
- `dist/migration-catalog.json` — generated catalog

## SOAP API: Postman collection

The OpenAPI spec covers REST only. For Automation Studio objects that you query through the SOAP API, there's a Postman collection and environment. The collection fetches and refreshes OAuth tokens automatically and saves `ContinueRequest` paging state. It renders each response's records as a table in Postman's **Visualize** tab. The collection overview and each request's description explain the SOAP envelope, filters, status codes, and what SOAP can't retrieve.

The JSON files aren't committed. `scripts/build-postman-soap-collection.mjs` generates them. You can get them in either of two ways:

- **From CI:** open the latest run of the **Build Postman collection** workflow in GitHub Actions and download the `sfmc-soap-postman` artifact.
- **Locally:** run `npm run postman:soap`, which writes them to `postman/` (gitignored).

Import both into Postman:

- `sfmc-soap-automations.postman_collection.json`
- `sfmc-soap.postman_environment.json` (set `subdomain`, `clientId`, `clientSecret`, and optionally `accountId`)

## Migration recipe model

Each recipe is a YAML file under `specs/migrations/` with a small, deliberately sequential shape:

```yaml
id: export-data-extension-rows
name: Export rows from a Data Extension
direction: export
source_system: salesforce-marketing-cloud
target_system: generic-json
family: data_extensions
prerequisites:
  scopes: [data_extensions_read]
  inputs_required: [data_extension_key]
steps:
  - id: kickoff
    operation_id: post_data_v1_async_dataextensions_key_rows_retrieve
    why: Start an async retrieve job against the target DE.
    inputs:
      key: { source: input, value: data_extension_key, required: true }
    outputs:
      requestId: $.requestId
  - id: await
    operation_id: get_data_v1_async_requestid_status
    polling:
      poll_operation_id: get_data_v1_async_requestid_status
      terminal_statuses: [Complete, Failed]
      interval_seconds: 5
      timeout_seconds: 900
    inputs:
      requestId: { source: step.kickoff.output.requestId, required: true }
  - id: fetch
    operation_id: get_data_v1_async_requestid_results
    inputs:
      requestId: { source: step.kickoff.output.requestId, required: true }
idempotency_notes: Async retrieve is read-only and safe to retry end-to-end.
```

Full schema: `specs/migrations/_schema.yaml`. Author guide: `specs/migrations/README.md`.

## Vendor extensions for migration

| Extension                  | Type                        | Meaning                                                                 |
| -------------------------- | --------------------------- | ----------------------------------------------------------------------- |
| `x-migration-direction`    | `import \| export \| both \| control-plane` | Role of this operation in a migration. `control-plane` means not a valid recipe step on its own (auth, sends, publish actions, etc.). |
| `x-bulk-capable`           | boolean                     | Operation natively processes arrays/batches without multiple calls.     |
| `x-polling-endpoint-of`    | `operationId`               | This operation is a status/results poll for the referenced kicker.      |

`x-migration-direction` is required on any operation referenced by a recipe step (enforced by `npm run check:migrations`). Elsewhere it is optional.

## Safety and idempotency guidance

Agents executing migrations should:

- **Acquire a token per tenant.** Keep the auth base URL separate from the REST base URL. Cache and refresh early.
- **Resolve BU/MID context explicitly.** A lot of SFMC confusion is really business-unit confusion. Accept BU input at the agent boundary; log resolved token context once; do not assume the token points at the intended BU.
- **Honor installed-package scopes.** Read and write routes in the same family often split across different scopes; send routes can differ from create/update routes. Use `x-sfmc-installed-package-scopes` on each operation, not endpoint-name guesses.
- **Handle 400, 401, 403, 404, 429, and 5xx consistently.** Back off on 429. Retry idempotent reads on 5xx. Do not blind-retry writes unless the operation is `x-bulk-capable: true` and the recipe declares an idempotency key.
- **Log request identifiers.** When SFMC returns a request id or correlation id, attach it to every step in the recipe run.
- **Prefer transactional messaging** over classic triggered sends for new work. Classic triggered sends are control-plane and should not appear as migration steps.
